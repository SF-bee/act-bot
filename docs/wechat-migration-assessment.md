# 微信迁移技术选型评估

- 日期：2026-10-05
- 状态：评估完成，供社团决策
- 适用范围：ACT 动漫社 QQ 群机器人（仓库 `act-bot`，群里对外身份 Yulia）
- 一句话结论：**个人微信群没有可长期依赖的合规自动化入口；不建议为此投入开发。QQ 群机器人适合转为低频资产保留。**

## 1. 结论摘要（TL;DR）

| 结论 | 说明 |
| --- | --- |
| ❌ 不建议迁移到个人微信 | 官方没有任何接口；非官方路线要么已被平台打击而停摆（Gewechat 已停止维护），要么封号风险高（PC Hook）。对社团账号是净损失。 |
| ✅ QQ 保留为低频资产 | 代码与数据本身跨平台、可交接，日常维护成本低；即使不新增功能也能继续用。 |
| ✅ 真要自动化触达，优先"单向通知" | 例如企业微信内部群机器人 webhook；不要追求个人微信里的双向命令交互。 |
| ⚠️ 真要群内交互，只有两条现实路径 | 接受非官方 Hook 的风险（小号 + Windows 常驻），或引导社团迁到有官方 API 的平台。 |
| ⏸️ 现在不要做"协议无关重构" | 没有明确且稳定的目标协议端之前，这是提前投资。等真的选定平台再动。 |

## 2. 背景

- 社团主战场已从 QQ 群转到微信群。
- 微信群缺少好用的机器人桥接，导致这个 QQ bot 很少被使用。
- 项目是从前学长手里接手的，本身是一套设计完整的 QQ 群机器人（NoneBot2 + OneBot v11 + SQLite）。

本报告回答一个问题：**这个机器人还要不要继续投入？要不要迁到微信？怎么迁？**

## 3. 现状盘点

### 3.1 代码资产与协议耦合

项目本身按"业务层 / 协议端分离"设计（见 `docs/design.md`、`docs/onebot-contract.md`），协议端可替换。但**当前实际只固化了 OneBot v11 一种协议**，业务层仍有直接的 OneBot 依赖。

| `src/plugins/help` | — | 读 |

**好消息**：权限、审计、统计、数据库、配置、备份、调度这些"社团资产"部分**与协议完全无关**，可以原样复用。真正要动的只是"收发消息"这一薄层。

## 4. 微信侧可行路径总览

| 类别 | 代表 | 能否群内交互 | 合规 | 现状 |
| --- | --- | --- | --- | --- |
| 官方 · 企业微信群机器人 | 企微群 webhook | ❌ 只能单向推送、不能收消息 | ✅ | 可用，但仅限企微内部群 |
| 官方 · 微信客服 | 微信客服 API / wechaty-puppet-wxkf | ❌ 客服会话，非群聊 | ✅ | 可用，不适用于社团群 |

| 无 | 个人微信群官方机器人 | — | — | **不存在** |

## 5. 方案逐一评估

### A. 维持 QQ（不迁移）

- **能力**：现有全部功能（欢迎、聊天、统计、权限、审计、备份）。
- **部署**：已有 macOS / Ubuntu / Windows / Docker 四套模板，可交接。
- **风险**：QQ 侧封号风险相对微信个人号低；项目已有换号流程。
- **维护成本**：低。不新增功能几乎不用管。
- **代价**：触达不到已迁微信的群友。

### B. 个人微信 · PC Hook（WeChatFerry + nonebot-adapter-wcf）

- **原理**：在 Windows 上 Hook 微信 PC 客户端收发消息（[WeChatFerry 文档](https://wechatferry.readthedocs.io/zh/latest/readme_link.html)）。
- **能力**：群消息、@、图片、文件、拍一拍等，能力最接近 QQ 方案。
- **部署**：**必须 Windows 常驻**，微信版本被适配情况绑定；官方 `wcfhttp` 已不再维护。
- **适配器**：[nonebot-adapter-wcf](https://github.com/OnlyAIGC/nonebot-adapter-wcf) 自述"按需实现，佛系更新"，可靠性无承诺。
- **风险**：社区多次报告 Hook 被扫描、封号；对社团实名账号是实打实的损失。
- **结论**：技术上可行，但**不建议作为社团长期方案**；若一定要试，只能用非重要小号，并接受随时失效。

### C. 个人微信 · iPad 协议（Gewechat 等）

- **原理**：逆向 iPad 协议、云端模拟登录，曾是最稳定的第三方方案。
- **适配器**：[nonebot-adapter-gewechat](https://pypi.org/project/nonebot-adapter-gewechat/)（2025-04 发布）。
- **现状（关键）**：Gewechat 仓库已改为**技术归档**并明确"本项目已停止维护"，历史服务、Docker 镜像、部署方式与技术支持**均不再提供**；其停止维护背景指向微信对违规获取用户数据的打击公告。AstrBot 等框架也有 issue 反馈"Gewechat 已无法登录"。
- **结论**：**不要再按旧教程部署**。这条路当前实际上已关闭。

### D. 企业微信（官方）

- **原理**：企业微信官方群机器人 / 应用消息。
- **能力边界（官方限制）**：
  - 群 webhook 机器人：**只能向企业内部群单向推送**，不能接收消息、不能被 @ 触发；
  - 官方 API 智能机器人：仅支持企业成员私聊 / 内部群 @ 对话；
  - **完全不支持外部群、不支持对接个人微信**。
- **适用**：如果社团愿意整体把沟通迁到**企业微信内部群**，可以用它做公告/通知推送。
- **代价**：需要全员装企业微信并使用内部群，和"大家已经在用的个人微信群"是两套体系。

### E. 协议无关重构（使能项，不是方案）

- **内容**：把 `events.py` 的规范化、插件的发送调用、适配器注册抽象成协议无关层，未来可接第二个适配器。
- **作用**：降低"换协议端"的成本。
- **局限**：**解决不了微信的封号与合规问题**——如果目标平台本身没有稳定接口，抽象得再好也没用。
- **建议**：等真的确定要接某个具体平台时再做。

## 7. 与现有架构的契合度与迁移工作量

现有领域事件层（`src/core/events.py`）已经把"读消息"部分做了规范化，是迁移的有利基础。工作量集中在两处：

1. **读侧**：`normalize()` 目前返回的是基于 OneBot 事件的领域事件；换适配器需为新协议再写一个规范化函数（接口不变，插件不受影响）。
2. **写侧**：`welcome.py` 的 `Message` / `MessageSegment` 与各插件的 `bot.send_group_msg` 需要抽象成"发送接口"。

粗估（**仅供参考**，取决于目标适配器成熟度）：

| 方案 | 涉及文件 | 粗估工作量 |
| --- | --- | --- |
| 最小可用（只接一个微信适配器，边接边改） | 10 处耦合 + 7 个插件 | 数人天～1 周 |
| 协议无关重构（抽出 adapter 层，长期可维护） | 同上 + 新增协议抽象模块 | 1～2 周 |

> 注意：工作量不是问题的主要矛盾，**平台的可持续性才是**。

## 8. 风险与合规

- **封号**：个人微信 Hook / 协议方案都在平台打击范围内；损失的是社团实名账号与群关系。
- **合规**：逆向平台客户端通常违反服务条款；学校社团账号尤其不建议冒此风险。
- **服务依赖**：第三方协议服务可能随时停止（Gewechat 就是活生生的例子），今天能跑不代表明天能跑。
- **数据主权**：个人微信的数据不属于社团资产，无法像 `data/act.db` 一样交接；换负责人即断档。
- **维护负担**：非官方方案需要持续跟进客户端/协议变动，对一届一换的社团是不可承受之重。

## 9. 决策树与推荐

```
社团还想要"群里自动互动"吗？
├─ 不想要，只要偶尔能发公告/资料
│   └─ ✅ 维持 QQ 低频使用；或若全员用企业微信，用内部群 webhook 做单向通知
│
└─ 想要
    ├─ 能接受封号风险 + 有 Windows 常驻机 + 愿意用非重要小号？
    │   ├─ 能  → ⚠️ 可试用 WeChatFerry Hook（小号、限频、随时准备失效）
    │   └─ 不能 → 引导社团改用一个有官方机器人的平台（QQ / 企业微信 / 飞书 / Discord）
    │
    └─ 是否愿意让全员迁移到新平台？
        ├─ 愿意 → ✅ 企业微信内部群（官方、合规，但仅单向/内部）
        └─ 不愿意 → ❌ 个人微信群没有合规的自动化方案，接受"没有机器人"或保留 QQ
```

**推荐**：
1. **首选**：QQ 保留为低频资产，不为"个人微信群交互"投入开发。
2. **次选**：如果确实需要自动化触达，做**单向通知**（企微内部群 webhook），不做群内命令交互。
3. **不做**：基于 Gewechat 的方案（服务已停）。
4. **谨慎**：WeChatFerry Hook 仅作为"可接受失效的小号试验"，不承载社团正式功能。

## 10. 若选择迁移的落地路线图（仅方向，不实施）

仅当社团明确选定平台后才执行：

1. 选定**有稳定接口**的目标平台（企业微信优先）。
2. 在该平台上做一个最小闭环（一个"接收→回复→落库"的冒烟）。
3. 若闭环成立，再评估把业务层抽象成协议无关层。
4. 数据继续复用 `data/act.db`，与协议解耦。

## 12. 待确认问题

1. 社团是否愿意为机器人整体迁到**企业微信内部群**？如果不愿意，个人微信方向基本无解。
2. 是否愿意接受"单向通知"这种弱化形态（只发通知，不做命令交互）？
3. 群里还有多少人偶尔用 QQ？如果接近为零，可直接考虑归档（保留数据与交接文档）。
4. 有没有非微信、但社团愿意接受的通知渠道（如公众号、飞书、Discord）？
